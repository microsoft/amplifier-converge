# Collaborative Capabilities Contract — v1 (DRAFT)

A proposed additional public seam for independently installed collaborative parts.
It does not amend or replace the settled service, agent-types or experience seams.

## Who builds against this

On-ramp owns projectless ideas and their promotion. Direction owns document
revisions and wording proposals. Operation owns the presentation of work.
Service owns record storage and command receipts. Agents owns native execution.
The experience SDK owns presentation transport. Method owns the document law;
the operating bundle owns the delivered supervisor and manager instructions.

## What it is

Each capability has one callable library behind its command line, agent tool and
collaborative view. An installation composes compatible immutable revisions.
The record adapter is explicit, local to one trusted owner and scoped by project.
This first adapter is an embedded public Service library used by several local
processes; it is not the single-process HTTP door promised by service.v1.
It does not silently redefine that door, run states, identity or merge authority.

## The promises

1. **One domain implementation per capability.** Presentation and command-line
   adapters call the same public actions. Operation delegates lifecycle commands
   to Agents; it never becomes a scheduler or a second run authority.
2. **Ownership stays visible.** Shared record mechanisms live in Service, native
   runtime mechanisms in Agents, transport in the experience SDK and method text
   in the operating bundle. Method stays document-only. Consumers use public APIs,
   never private tables or a neighbour's source path. No consumer carries a divergent copied core.
3. **Changes have receipts.** Mutations carry a stable request identifier and
   exact arguments. An exact retry returns its receipt; changed arguments under
   the same identifier are refused. Revisions and project boundaries are checked.
4. **Conversation authority stays native.** Native session histories retain their
   own identifiers and storage. Domain records hold ideas, documents, work,
   evidence and bounded observations, never a replacement conversation history.
5. **Movement does not replay work.** An idle manager can be stopped and explicitly
   reconnected with the same native session. No earlier instruction is submitted
   during installation. Active work is allowed to finish or explicitly stopped.
6. **A result keeps its meaning.** Turn ended, work reported, file bytes observed,
   semantic check and steward acceptance remain distinct. A retained draft or
   visible selection is not permission to execute or evidence of ratification.
7. **Sources can be reviewed and reproduced.** Every package declares its source
   revision and dependencies. Existing public surfaces remain intact. A source
   update stages new packages, tests them, then changes registrations while idle.

## Not in this proposal

A remote multi-user authority model; automatic compatibility with the existing
service.v1 HTTP records; a final domain migration to that service; interchangeable
native histories; new runtime adapters; changes to any settled contract.
The trusted-local adapter deliberately exposes its current limitation instead of
claiming the settled single-process service invariant has already been met.

## How the kit checks it

- Install each package from immutable repository references in a clean environment.
- Call the same action through library, command line and actual tool transport.
- Retain exact retry, stale revision, project-scope and lost-owner refusal tests.
- Observe packaged collaborative resources without a development source path.
- Compare saved projects, documents, receipts and native history across adoption.
- Reconnect without adding a run or a user turn; observe original native IDs.
- Existing part tests remain separate from the proposed adapter tests.
- Count the added implementation as part of its owner's body; any exceeded
  settled ceiling remains a visible proposal obligation, not hidden by packaging.

## Open questions

How the embedded record adapter should meet the existing single-process service
seam, and where the native session adapter ultimately moves under sessions.v1,
remain explicit follow-up design questions. This proposal authorizes neither a
new repository nor an unreviewed migration of the established service store.
