# Narrow workflow and handback acceptance plan — September 23, 2026

A repeatable next trial, not evidence that it has passed. It closes the specific
gaps in the [retrospective](RETROSPECTIVE-20260923.md) before using a full product
build as the workflow test. No new generic host interface is assumed or authorized.

## Preparation and evaluator boundary

Use the [merged follow-up record](RETROSPECTIVE-20260923.md#follow-up-repairs-merged-after-the-trial)
as the candidate starting point: portable instructions 0.4.25, runtime 0.2.28,
Operations 0.2.30 and optional bundle 0.2.18/module 0.1.13. Qualify the intended
combined installation and each role's actual resolved resources before the
trial; separate wheel checks and a merged PR do not prove adoption. Record any
later source revision explicitly rather than silently substituting it.

Use a fresh disposable workspace, domain store and Unified conversation. First
confirm the prior trial is quiet before changing shared capability bindings;
preserve prior histories, source returns, attempts and services. Do not equate
foreground idle with an idle independent manager. Use the owning public stop or
adoption path only when explicitly intended.

Record the exact installed package sources, role instruction hashes, configured
and effective model/effort, current capability schemas, and scoped project/native
identities privately. Check the actual installed tool cohort through public
discovery: On-ramp, Direction, Possibly and Operations. Do not count an offline
fixture as an installed capability. The narrow test may use only a subset; mark
unused capabilities **not exercised** rather than claiming full-flow acceptance.

Capture the initial bindings, then require every later observation to match that
scope. A changed binding, ambiguous project or missing observation is a failed or
inconclusive observation, not permission to inspect another project's newest run.
Keep routine observations bounded and only retain relevant public records.

The evaluator uses the visible customer conversation and browser. It does not
name lifecycle APIs, supply product code, run product checks, launch a replacement
service, repair Git identity or manually publish a result. Implementation and
engineering recovery belong to the native manager and its tracked workers. A
technical intervention makes the unaided customer-path gate inconclusive and
must be recorded separately.

## Customer sequence

1. Ask: “I'd like a little greeting page for our club. I want to type a greeting
   and change the background color. Please make a real page I can try in the
   browser. Let me know when it's ready and bring it up for me, so I don't have to
   keep checking.”
2. Try the controls that actually appear. If they work and the direction fits,
   say: “This is the right direction. Please turn it into a little app I can keep
   using on this computer. I'd like to save a few different greetings and have
   them still be there after I close it and come back. Let me know when the
   working app is ready and open it for me.” If they do not work, give ordinary
   product feedback instead of the scripted approval.
3. Leave the conversation idle through at least three scheduled observations and
   then until the admitted watch completes or expires. Do not send a status prompt
   that substitutes for automatic return. Use the actual accepted time limit;
   do not reset it to erase a failure.
4. On return, use the exact delivered app. Save two distinct greetings/colors,
   close and reopen it through the documented route, and restore both. Capture
   what happened in the customer browser, independently of worker/manager checks.

## Score each boundary separately

| Gate | Pass evidence | Failure or unproven boundary |
| --- | --- | --- |
| Ordinary collaboration | Customer can try/revise the idea and give meaningful approval before implementation | An automatically selected preview or a technical evaluator brief substitutes for customer intent |
| Native implementation | Actual admitted item, wave and isolated worker with bounded attempts; correct role model policy | Foreground HTML generation or a helper delegate counted as the implementation lane |
| Contract recovery | Any malformed mutation is refused without effects; correction uses the advertised contract and stable request identity | Hidden side effect, uncertain replay, evaluator-supplied API repair or budget reset |
| Manager acceptance | Exact returned source, declared checks run by the manager before/after integration, preserved failures and attempts | Worker assertions, unrelated check results, modified checks or abandoned failures treated as acceptance |
| Selected result | A current exact review/publication result selected through its public owner, with evidence and known gaps | Pre-run continuation, an old report or a process exit used as current success |
| Retained opening | Exact URL and assets, observed availability, service ownership/lifetime and supported opening path recorded | Temporary test server or static HTML shell substituted for a live application |
| Customer usability | Real controls and two-preset reopen behavior work in the delivered opening | HTTP 200, screenshots alone or an accepted open request treated as browser acceptance |
| Watch sequencing | Complete required task bookkeeping before arming; exact caller/task/run binding retained | Receipt-only task updates after arming; genuine later correction ignored rather than invalidating normally |
| Accurate automatic return | Without another customer turn, report current evidence and its limits, select/open the intended result, and end the watch once | Claims based on historical zero-work context; expiry represented as completed/stopped manager; missing proof invented |
| Duplicate and correction safety | After terminal handling, observe a later eligible occurrence/restart boundary with no second terminal notice; separately verify a genuine task correction prevents stale observation | Deduplication claimed immediately at the first terminal notice; old authorization reused after correction |
| Quiet/cost behavior | Record public scheduled messages, notifications and provider turns separately | Calling pending execution “quiet” only because the assistant did not reply |

Run the genuine-correction case separately from the successful handback case so
the correction does not invalidate the very watch being used to prove completion.
Do not weaken the existing task revision or authorization guard.

## Decision at the boundary

Retain a dated result with exact installed source references, PASS/FAIL/UNPROVEN
per gate, observed time window, product check versus customer check, and any
evaluator intervention. If the watch expires while a manager still works, report
both facts. Preserve the work and do not silently rearm, restart or abandon it.
Published fixes that were not installed during the trial receive separate source
qualification, never a retroactive live pass.

If narrow acceptance passes, follow with a real four-capability collaboration:
retain a rough idea, revise Direction, compare and preview alternatives through
the actual Possibly installation, make an explicit decision, observe manager work
in Operations, and return to an earlier capability after feedback. Repeat the
portable reasoning/checked-work journey in CLI/TUI text without a canvas. These
are follow-on validations, not a checklist satisfied by opening four views.

The [unapproved generic host proposal](UNIFIED-CHECKPOINT-20260923.md#unapproved-host-proposal)
has a different future acceptance bar: pending observations would make zero
provider calls, public chat messages and customer notifications while retaining
audit records, followed by one actionable handback. That bar requires a reviewed
host contract; the current Converge-only changes do not implement it.
